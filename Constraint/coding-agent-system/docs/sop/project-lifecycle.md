# 多 Coding Agent 项目全生命周期 SOP

## 适用范围

本 SOP 的直接配置入口聚焦 Codex 与 DSH Desktop / 官方 DeepSeek Harness；既有 Claude Code adapter 可作为兼容入口。流程从空目录开始，覆盖需求发现、配置初始化、应用脚手架、项目事实采集、规格、垂直切片、实现、专项质量检查、审查、交付和规则演进。

本 SOP 约束 Agent 的工作方式，但不替代 permissions、sandbox、hooks、CI 或人工审批。自然语言规则、skill 描述和子 Agent 任务都不构成权限授予。

本系统的 `init-project` 只生成 Agent 配置、skills 与选定的技术栈规则，不生成应用框架、数据库或部署环境。应用脚手架必须根据已确认的技术方案另行选择。

## 完成定义

一个开发任务只有同时满足以下条件，才可报告「完成」：

- 已确认的验收条件均有对应证据。
- 与改动风险相称的测试、静态检查、构建或运行检查已执行并通过。
- 用户可见改动已在实际渲染界面中检查；仅阅读代码不算视觉验证。
- 数据库变更已说明前向路径、恢复路径、兼容窗口和未验证的生产假设。
- 没有遗留临时日志、调试开关、测试数据、一次性脚本或孤儿代码。
- 实际改动没有超出任务授权范围。
- 未执行的检查、外部依赖和剩余风险已明确列出。

## 权限基线

### 默认可自主执行

用户明确要求分析、修改或构建后，Agent 可在指定工作区内执行与任务直接相关的只读搜索、局部文件编辑、已有测试、lint、typecheck、build 和隔离 smoke test。执行前仍需确认项目已有命令和工作区状态。

### 必须在动作前单独确认

以下动作不得从「实现功能」「修复问题」或 skill 调用中推导授权：

- commit、push、merge、创建或更新远程 PR / issue。
- 发布、部署、生产写入、真实消息发送、付费调用和其他外部副作用。
- 安装、升级或删除依赖；改变 lockfile 或全局开发环境。
- 读取 secrets、`.env`、凭据、认证 header、私钥或 PII。
- 删除、批量移动、覆盖关键配置、放宽权限、关闭安全校验或执行不可逆操作。
- 连接或修改真实数据库；运行可能长时间锁表、全量回填或删除数据的 migration。
- 会改变架构、数据模型、权限、兼容性或核心 UX 的未决方案。

授权必须包含明确对象和范围。例如，「允许对 staging 数据库执行 migration dry-run」不等于允许访问 production，也不等于允许部署。

### 授权失效条件

出现以下任一情况时，先前授权不能自动扩大：

- 目标环境、数据集、仓库、分支或外部系统发生变化。
- 实际操作的副作用大于授权时的说明。
- 发现新的秘密、权限需求或不可逆风险。
- 计划从只读检查变为写入，从本地变为远程，或从免费操作变为付费调用。

## 能力选择边界

| 机制 | 适用问题 | 不应承担的职责 | 启用门槛 |
| --- | --- | --- | --- |
| `AGENTS.md` / `.claude/CLAUDE.md` | 所有任务都需要的稳定行为契约、项目事实入口和安全边界。 | 长步骤教程、快速变化的框架细节、强制安全控制。 | 内容跨多数任务稳定，并且会影响每次决策。 |
| Skill | 需求发现、规格、TDD、调试、审查等需要判断和分支的工作流。 | 授权外部写入、替代项目事实、强制阻止危险命令。 | 描述与当前任务匹配；显式调用型 skill 还需要用户或编排器明确选择。 |
| Hook | 可确定判断的命令前检查、格式校验、记录和通知。 | 复杂产品判断、完整安全边界、跨平台共同配置。 | 平台确实支持、规则可快速且幂等执行、误报和失败模式已评审。 |
| MCP | 获取实时外部事实，或调用本地没有的受控外部能力。 | 可由仓库、官方文档或本地工具回答的问题；隐式外部写入。 | 服务在白名单中；先启用最小只读工具；凭据不进入项目；写操作逐项授权。 |
| Subagent | 可独立研究、实现非重叠模块、运行专项审查或并行验证。 | 共享同一文件的并发编辑、替父 Agent 做最终集成、绕过权限确认。 | 子任务有清楚的输入、文件边界、完成标准和回报格式。 |
| permissions / sandbox / CI | 必须确定性限制的路径、工具、命令和合并质量门。 | 解释产品意图或替代验收标准。 | 需要机器强制执行，并且平台或仓库已有可验证机制。 |

### 选择顺序

1. 先判断问题能否由仓库事实和已有工具解决。
2. 再判断是否需要一套带分支的可复用方法；需要时选择 skill。
3. 若规则必须每次确定性执行，评估 hook、permissions 或 CI。
4. 只有需要实时外部数据或外部能力时才启用 MCP。
5. 只有任务可以独立验收且文件或状态边界不冲突时才派发 Subagent。

## 消融式删减检查

用户提出「进行消融实验」时触发本检查；本节是静态工作流协议，不表示已完成严格模型消融实验。非琐碎设计或实现先取得首次可信 green，再冻结 Baseline：首次满足的验收、不变量、风险和命令/方法，以及已有证据层级。

Candidate 只可来自本轮新增设计或当前 diff，且每次只处理一个候选。为候选记录 Trace：它是否由当前需求、不变量、失败模式或风险支撑；没有依据时写 `NONE`。不得以此清理历史无关抽象，也不得删除由正确性、安全、权限、数据完整性、兼容性、并发/失败语义、可访问性、可观测性、性能、migration、恢复、回滚或已批准 UX 支撑的 seam。

对单一 Candidate 作 `remove | defer | retain` 决定；`remove` 后必须使用同一验收和相关回归复验，`retain` 或 `defer` 必须写明 Trace。完成所有逐项决定后，运行与当前改动风险相称的最终相关回归。代码行数、文件数、抽象层数或单次 green 均不能单独判定更优；不得删除测试、降低 acceptance 或扩大写入、依赖、外部动作、生产权限和既有授权边界以制造 green。

琐碎任务可缩放为报告「无可安全删减候选」及其依据。无法执行、不能重建时序或仍有残余风险时，必须在 Limitations 中如实列出；contract-only 或静态检查不得表述为真实 Agent 运行。

非琐碎任务的证据使用以下唯一结构：

```text
## Ablation evidence
- Baseline: 首次满足的验收、不变量、风险和命令/方法。
- Candidate: 仅本轮新增的可删减设计或实现。
- Trace: 当前需求、不变量、失败模式或风险；无则写 NONE。
- Decision: remove | defer | retain。
- Verification: 同一验收/回归的方法、结果与证据层级。
- Limitations: 未执行、不可重建时序或残余风险。
```

## 生命周期总览

| 阶段 | 主要产物 | 进入下一阶段的门槛 |
| --- | --- | --- |
| 0. 任务建档 | 任务简报、权限边界、验收草案 | 目标和风险范围可执行。 |
| 1. 需求发现 | 已确认决策、假设、非目标和验收场景 | 重大产品分支已关闭或明确延期。 |
| 2. 初始化 | Agent 配置树、选定模块、应用脚手架 | 目录安全，基础运行路径可验证。 |
| 3. 项目事实采集 | 事实清单、命令清单、影响图 | 关键实现判断有仓库证据。 |
| 4. 规格 | 可实现、可验收的 spec | 需求与验收双向可追溯。 |
| 5. 垂直切片 | 无环依赖图和独立 tickets | 每个切片可单独交付并保持可用。 |
| 6. 实现 | 小而完整的行为增量 | 每个增量有新鲜验证证据。 |
| 7. TDD 与调试 | red→green 证据或根因证据 | 原症状消失且相关回归通过。 |
| 8. 数据库专项 | migration 与恢复方案 | 隔离环境验证通过，生产未知项已标注。 |
| 9. 前端专项 | 实际页面与状态检查记录 | 目标 viewport、状态和可访问性通过。 |
| 10. 双轴审查 | Standards / Spec findings | 重要 finding 已处理并复验。 |
| 11. 交付 | 改动摘要、验证矩阵、剩余风险 | 用户可据证据接收；外部动作另行授权。 |
| 12. 规则演进 | 待审候选或经批准的规则变更 | 有证据、无冲突、可回滚且人工批准。 |

## 阶段 0：任务建档与权限确认

### 前置条件

- 已收到一个可定位到具体工作区的请求。
- 能读取适用的用户级与项目级指令；无法读取时先说明限制。
- 当前任务没有要求立即执行未授权的外部或破坏性动作。

### 动作

1. 用一句话写明目标结果，而不是计划采用的技术。
2. 列出已知输入、明确非目标、可观察验收条件和时间或兼容性约束。
3. 区分事实、决定、假设和未决项。可从仓库查明的事实不询问用户。
4. 标记数据、权限、外部系统、依赖、部署和不可逆操作风险。
5. 确定当前授权只覆盖诊断、文档、代码编辑，还是还包含特定外部动作。
6. 非琐碎任务建立短计划；每次只保留一个进行中的步骤。

### 产物

- 任务简报：目标、范围、非目标、验收条件、约束、未决项。
- 权限清单：当前允许、需要确认、明确禁止的动作。
- 初始验证矩阵：每项验收条件对应的预期证据。

产物可保留在当前任务上下文中。只有项目已有正式记录位置，或用户要求持久化时，才创建新文档。

### 质量门

- 任何会改变架构、数据、权限、安全、兼容性或核心 UX 的缺口均已识别。
- 完成标准可由测试、运行行为、页面检查或明确人工验收判断。
- 计划没有把 commit、部署、外部写入或依赖安装当作默认收尾动作。

### 停止与恢复

- **停止：** 工作区、目标对象或授权范围不明确；检测到与任务重叠的未知改动；必须读取秘密才能继续。
- **恢复：** 用户明确范围或授权；协作者说明变更归属；提供脱敏 fixture、非生产环境或可替代的公开接口。

## 阶段 1：需求发现

### 前置条件

- 需求仍存在会影响用户流程、数据、权限、兼容性或优先级的分支。
- 用户同意进行需求发现；`product-discovery` 是显式调用型 skill，不能只因任务模糊而静默启动长访谈。

### 动作

1. 显式调用 `product-discovery`。
2. 先阅读已有 PRD、设计、问题记录、分析数据和相关实现，消除可自行查明的问题。
3. 建立依赖感知的决策树。每轮只询问前置决策已确定的当前问题。
4. 每个问题给出真实选项、影响和建议；不使用没有差异的伪选项。
5. 持续更新目标用户、主流程、失败行为、成功信号、约束和非目标。
6. 若需要比较状态模型或 UI 结构，可调用 `safe-prototyping`。原型必须隔离、一次只回答一个问题，并提前定义清理方式。
7. 请用户确认最终理解。未确认的内容保持为假设或未决项。

### 产物

- 已确认的用户问题、目标用户和期望结果。
- 主流程、异常流程和关键状态。
- 决策、假设、非目标、风险和未决项。
- 可区分「做对」与「做出来」的验收场景。

### 质量门

- 所有会改变架构、数据、权限、UX 或兼容性的分支均已决定或明确延期。
- 原型结论有可观察证据；正式实现不依赖一次性原型代码。
- 没有把产品建议写成已经确认的决定。

### 停止与恢复

- **停止：** 决策依赖业务负责人；需要真实客户数据、付费调用或生产行为才能验证；新答案推翻核心前提。
- **恢复：** 获得负责人决定、脱敏样本或针对特定外部操作的授权；更新决策树并重新确认受影响结论。

## 阶段 2：从空目录初始化项目

### 前置条件

- 已确认项目根目录、目标平台、预期技术栈和应用目录布局。
- 目标项目目录不存在，或是一个真实且完全空的目录；不要使用符号链接作为目标。
- 已阅读[安装与隔离验证](../installation.md)，并在配置系统源码上运行 `validate`。
- 已确认哪些 `--stack` 模块与计划技术栈相关。不要为了「以后可能用」而启用全部模块。

### 动作

#### 2.1 生成 Agent 配置

1. 切换到 `Constraint/coding-agent-system/`。
2. 运行 `python3 tools/agent_system.py render-templates` 和 `python3 tools/agent_system.py validate .`。前者列出完整目标映射，不区分内容是否变化；漂移以 `validate` 为准。存在未应用的共享快照漂移时，先审查 canonical core，执行 `render-templates --apply` 并审查可用的版本历史或逐文件变化；不要继续项目 apply。
3. 运行 dry-run。`--stack` 可重复：

   ```bash
   python3 tools/agent_system.py init-project /absolute/path/to/project \
     --stack typescript-nextjs \
     --stack frontend-visual-quality \
     --stack file-document-governance
   ```

4. 检查输出首行为 `DRY-RUN`，并逐项审查 `display path -> canonical absolute destination` 映射；祖先 alias 会显示解析后的真实路径。
5. 使用完全相同的参数追加 `--apply`：

   ```bash
   python3 tools/agent_system.py init-project /absolute/path/to/project \
     --stack typescript-nextjs \
     --stack frontend-visual-quality \
     --stack file-document-governance \
     --apply
   ```

6. 检查 `.agents/generated-manifest.json` 中的 `stacks` 与已确认模块一致；该文件使生成物校验能检测所选规则被删除。
7. 运行 `python3 tools/agent_system.py validate-generated --kind project --root /absolute/path/to/project`。该检查允许初始 draft 画像。
8. 检查根 `AGENTS.md`、`.agents/project-profile.md`、空的 `.agents/memory/candidates.jsonl`、默认关闭的 `.agents/controls/`、`.claude/CLAUDE.md`、`.agents/skills/`、平台配置和选定的 `.agents/rules/`。根 `AGENTS.md` 的受管路由块必须逐项列出已选模块路径和触发范围；只有把模块文件复制进 `.agents/rules/` 而没有根路由不算完成。初始化器不应生成实际 policy `.agents/controls/change-policy.json`。项目根不应出现 `AGENTS.override.md`、`AGENTS.local.md`、`CLAUDE.md` 或 `CLAUDE.local.md` 这四个指令阴影文件；`.claude/CLAUDE.md` 的首个逻辑行应为 `@../AGENTS.md`。

`init-project` 不创建 Git 仓库。尚无 Git 根时，从生成项目根启动 DeepSeek Harness；不要从 `src/` 或 `apps/*/` 等嵌套 cwd 启动后再假定根规则已加载。没有可识别 Git 根时，Harness 的 skill 发现会以当前工作目录作为项目根，从而遗漏真正项目根的 `AGENTS.md` 或 `.agents/skills/`。这些发现行为以默认 spine 已启用 `agent-instructions`、skill registry、tool consumer 与 skill filesystem plugins 为前提；自定义 preset 必须按实际组合复核。

将 Claude 入口放在 `.claude/CLAUDE.md` 只避免 Harness 的初始根候选冲突。Harness 成功访问 `.claude/` 后仍可能动态发现该文件，且不会解释首行 `@../AGENTS.md` import；不要在该文件复制根契约或增加与 Harness 冲突的规则，交付前按目标版本实测。

当前安装器不会自动跟随 `CODEX_HOME`、`CLAUDE_CONFIG_DIR`、`DSH_HOME` 或 `DSH_AGENTS_HOME`。先在隔离 home 生成并审查，再按当前客户端核实配置根，最后人工复制到自定义位置；不要把 `--home` 误当作任一平台配置根参数。只要用户安装 target 包含 Codex 或 DeepSeek Harness，dry-run 都应同时显示共享 `.agents/skills/` 和七个 DSH explicit-only overlay；同机使用多平台时建议选择 `--target all`。

`validate` 只校验本配置系统源码。不要对生成后的项目目录运行 `validate` 并把失败误判为项目配置损坏。

#### 2.2 生成应用脚手架

1. 从已确认的技术方案选择框架官方脚手架和当前支持的参数；不要假定包管理器、版本或命令。
2. 在运行前检查脚手架是否要求目标根目录为空。
3. 若脚手架支持已有配置文件的目录，先 dry-run 或检查帮助，再在项目根执行。
4. 若脚手架强制要求空根目录，停止根目录执行。选择以下经确认的方案之一：
   - 在已决定的子目录生成应用，例如项目采用 monorepo 或明确的 `apps/` 布局。
   - 在独立空目录生成脚手架，审查后逐文件合并。合并必须保留项目根 Agent 配置，且不能静默覆盖。
   - 暂停并扩展初始化器，使其支持经过测试的非空目录合并；不要用临时移动文件绕过空目录保护。
5. 脚手架需要联网、下载包、安装依赖或改变全局环境时，在动作前取得明确授权。
6. 生成后只使用实际存在的 scripts 启动最小 smoke test。

### 产物

- 用户级短常驻内核渲染得到的入口、项目画像路由器与三平台适配入口。
- draft 项目画像、空的 Memory 候选队列和默认关闭的 controls 说明。
- Canonical skills、平台调用适配副本、完整 supporting resources，以及选定且从根可达的技术栈/文件治理模块。
- 经确认的应用目录、依赖清单、基础配置和启动入口。
- 初始化决策记录：平台、模块、布局、工具和未执行的联网步骤。

### 质量门

- 生成前目标目录确实为空；apply 没有覆盖既有项目。
- dry-run 与 apply 使用相同参数，apply 输出首行为 `APPLIED`。
- `validate-generated --kind project` 返回 `VALID-GENERATED`。
- 当前阶段只要求画像结构为合法 draft；不把该结果表述为画像已 ready。
- 只加载与项目相关的技术栈模块。
- 框架脚手架没有覆盖 `AGENTS.md`、`.claude/CLAUDE.md` 或平台配置，也没有在项目根新增会被 DeepSeek Harness 默认 `agent-instructions` plugin 作为初始候选发现的 `CLAUDE.md`。
- 至少完成一个本地、隔离的基础运行或静态解析检查；未安装依赖时明确标注未验证。

### 停止与恢复

- **停止：** CLI 报 `Destination must be empty`；脚手架要求空根目录；需要未授权的联网或依赖安装；生成结果将覆盖已有配置。
- **恢复：** 选择新的空目标或经确认的子目录布局；先在隔离目录验证；取得依赖安装授权；对冲突文件逐项人工合并。

## 阶段 3：项目事实采集

### 前置条件

- 项目目录已生成，并且不再处于未知的部分写入状态。
- 已读取根指令、就近目录指令、工程规范和已有开发记录。
- 只读检查可以覆盖目标模块，不需要秘密或生产访问。

### 动作

1. 定位规范源：依赖清单、lockfile、编译配置、应用入口、路由、schema、migration、测试、CI 和部署描述。
2. 记录实际语言、运行时、框架、包管理器、目录边界和生成文件规则。文件名线索必须由依赖或调用关系确认。
3. 从 scripts、CI 或开发文档提取可用的 test、lint、typecheck、build、migration 和启动命令。不要发明命令。
4. 搜索目标行为的实现、调用点、公共接口、错误处理、测试先例和相邻模块。
5. 建立最小影响图：输入边界、状态或数据流、输出边界、外部依赖、失败边界。
6. 将无法从仓库确认的环境、数据规模、生产拓扑和兼容窗口标为未知。
7. 只有探索区域独立时才并行派发 Subagent。每个 Subagent 只负责一个清晰区域，以只读结果和证据路径回报；父 Agent 负责去重和集成。
8. 把已确认事实写入 `.agents/project-profile.md` 的七个标题域：业务与安全不变量、权威修改入口、联动关系、Do NOT 与受保护区域、精确 Definition of Done、权威资料与冲突顺序、局部风险。active 每域使用 `- Fact:`、`- Decision:` 或 `- Not applicable:`，下一行缩进写受控 `Source:`；`Not applicable` 必须说明不适用边界，不能只写 `N/A`、“无”或“待定”。Assumption 与 Open question 留在调查记录中。每个规定 H2 只能出现一次，不新增未知 H2；当前任务相关的实质缺口仍未关闭时保持 `profile_status: draft`。
9. 七域都已有结构化、非低信息的 Fact / Decision / Not applicable，且每条都由项目相对路径、可复现命令、http(s) URL 或带日期与上下文的维护者确认支持后，把状态改为 `profile_status: active`，再运行：

   ```bash
   python3 /absolute/path/to/coding-agent-system/tools/agent_system.py \
     validate-generated \
     --kind project \
     --root /absolute/path/to/project \
     --require-ready-profile
   ```

10. 如果项目确有必须机器阻止的受保护路径或联动变更，由维护者从 example 创建 `.agents/controls/change-policy.json`，先手工验证检查器，再显式接入既有 hook 或 CI。没有接入时，controls 保持关闭；不要把文件存在等同于控制已执行。

### 产物

- 项目事实清单及证据位置。
- 可执行命令清单及其来源。
- 目标行为的调用图、数据流或状态流摘要。
- 已知约束、未知项和需要用户决定的事项。
- 状态可信的项目画像；未完成时保持 draft，并列出阻止 active 的具体缺口。

### 质量门

- 每个技术选型和命令都能追溯到仓库或当前官方文档。
- 已区分生成文件与规范源文件。
- 没有读取或输出 `.env`、token、凭据和 PII。
- Subagent 结果已由父 Agent 对照原文件核实，不能仅凭摘要下结论。
- 进入实现前，`--require-ready-profile` 返回 `VALID-GENERATED`；如果仍为 draft，则任务只能继续做事实调查、风险收窄或明确获批的有限工作。

### 停止与恢复

- **停止：** 事实来源冲突；目标文件存在来源不明且重叠的变更；关键行为只能通过秘密或真实外部系统确认。
- **恢复：** 由维护者确定规范源；协作者说明工作区变更；提供脱敏 fixture、只读测试环境或官方接口说明。

## 阶段 4：形成可实现规格

### 前置条件

- 需求发现结论已确认。
- 项目事实和关键未知项已整理。
- 用户明确要求产出或更新规格；`specification` 是显式调用型 skill。

### 动作

1. 显式调用 `specification`。
2. 写明问题、期望结果、参与角色、主流程和异常流程。
3. 将功能需求写成可观察行为，不写逐文件施工清单。
4. 对每项需求定义验收场景；对每个验收项反向确认其需求来源。
5. 适用时写明数据、权限、兼容性、失败行为、迁移顺序和恢复原则。
6. 把实现决定、仓库事实、建议、假设和未决项分开。
7. 选择最少的 public test seam。新增 seam 若会改变架构，先请求确认。
8. M04 的 MVP、non-goals 和 no-build 已承担产品范围消融；规格化不得借消融式删减检查静默删除已确认需求。
9. 请用户审阅。写入本地文件需要用户已要求文档产出；写入真实 issue tracker 需要针对该次外部写入的授权。

### 产物

- 已确认或明确标为草稿的规格。
- 需求—验收双向追踪表。
- 非目标、兼容性边界、失败行为和开放问题。
- 预期验证层级与无法在本地验证的事项。

### 质量门

- 另一个 Agent 不需要猜测产品行为即可实现。
- 每项需求至少有一个验收方式；每个验收项均有需求或风险来源。
- 未决项没有伪装成强制实现要求。
- 规格没有隐式授权依赖安装、生产访问、Git 或外部写入。

### 停止与恢复

- **停止：** 新事实推翻已确认需求；测试 seam 会实质改变架构；关键失败行为或权限规则未决定。
- **恢复：** 回到需求发现阶段修订决策；由用户批准 seam 和边界；更新规格与追踪表后再次确认。

## 阶段 5：拆分垂直切片

### 前置条件

- 已有确认的规格或足够明确的轻量验收条件。
- 用户明确要求拆票或制定实施切片；`vertical-ticketing` 是显式调用型 skill。

### 动作

1. 显式调用 `vertical-ticketing`。
2. 按用户可观察行为拆分切片，使每个切片贯穿所需的数据、服务、界面和验证层。
3. 每个切片写明交付行为、`Blocked by`、验收条件和必要的非目标。
4. 对本轮新增的架构、seam 或 ticket 逐项执行消融式删减检查，记录保留依据；不得借此绕过架构确认或删减已确认规格。
5. 只添加真正阻止开始的依赖边，并检查依赖图无环。
6. 对无法持续保持可用的大规模机械迁移，使用 expand–migrate–contract。
7. 只有文件和状态边界不重叠时，才把切片并行分配给 Subagent。父 Agent 保留公共接口、依赖图和最终集成责任。
8. 真实 tracker 写入仍需单独授权；默认只形成本地或对话中的草稿。

### 产物

- 独立可验收的垂直 tickets。
- 无环依赖图和可并行 frontier。
- 每个 ticket 的完成证据类型与集成边界。

### 质量门

- 每个切片完成后项目保持可运行或至少保持原有 green 状态。
- 所有规格要求恰好被覆盖，没有遗漏、重复 ownership 或隐藏集成阶段。
- Subagent 不会同时修改同一文件、schema 区域或共享状态。

### 停止与恢复

- **停止：** 缺少产品决定；依赖图成环；切片只能按技术层横切；并行任务争用同一文件或接口。
- **恢复：** 返回规格阶段；缩小或重组切片；先完成公共接口切片，再重新计算并行 frontier。

## 阶段 6：按切片实现

### 前置条件

- 当前切片的验收条件、文件范围和依赖已明确。
- 工作区状态已检查；没有与当前范围重叠的未知变更。
- 已选择最小充分验证命令。

### 动作

1. 先搜索已有实现、工具函数、接口和测试，再决定复用或新增。
2. 在 public seam 上建立可失败的反馈信号。新行为优先进入 TDD 循环。
3. 只实现当前切片需要的最小代码；不提前完成后续 ticket。
4. 保持项目既有命名、错误结构、依赖注入、状态管理和目录边界。
5. 每完成一个行为增量，运行最窄验证；公共接口或共享模块改变后扩大验证范围。
6. 每个行为增量首次可信 green 后、Subagent 集成前，只对当前 diff 的新增候选逐项执行消融式删减检查，并以同一验收复验。
7. 若使用 Subagent，父 Agent 在每个结果返回后检查 diff、测试证据和越界改动，再按依赖顺序集成。
8. MCP 只用于仓库无法提供的实时事实。默认启用只读工具；外部 mutation 必须在调用前获得对象级授权。
9. Hook 只执行已配置的确定性检查。Hook 失败必须可见；不通过跳过 hook 或放宽权限制造成功。

### 产物

- 当前切片的最小、可审阅 diff。
- 与行为绑定的测试和运行证据。
- 必要的文档或开发记录更新。
- 未解决事项和下一切片的已知前置条件。

### 质量门

- 每行改动都能追溯到当前切片或由其引发的必要修正。
- 没有新增无调用方抽象、无依据依赖或无关格式化。
- 保留的新抽象能追溯到当前需求、不变量、失败模式或风险。
- 当前测试通过，并且风险相称的直接回归检查通过。
- 输出没有 secrets、调试代码、临时数据或截断后被误判为成功的日志。

### 停止与恢复

- **停止：** 第三次验证仍未解决同一问题；修改开始互相干扰；发现架构或规格缺口；需要新增依赖或扩大权限。
- **恢复：** 停止叠加 patch，审查数据流与失败边界；回到规格或调试阶段；用户批准新的依赖、架构或权限后重新制定切片。

## 阶段 7：TDD 与系统化调试

### 前置条件

- 已定义可观察行为或精确故障症状。
- 已找到项目现有 public seam、测试先例和最窄可执行命令。

### 动作

#### 7.1 新行为或已知修复

1. 调用 `tdd`。
2. 写一个只描述当前行为的测试。
3. 运行测试，确认它因目标行为缺失而失败。编译错误、环境错误和意外通过都不算 red。
4. 写最小生产代码使测试通过。
5. 重跑目标测试及直接相关回归。
6. 只在 green 上重构；每次重构后重新验证。

#### 7.2 根因不明、flaky 或性能问题

1. 调用 `systematic-debugging`。
2. 定义 exact symptom、预期行为和一个 pass/fail command。
3. 缩减复现输入；每次删除条件后重跑，保留真正必要的条件。
4. 为每个根因假设写出可证伪预测，一次只改变一个变量。
5. 根因有证据后，写回归测试并观察失败，再应用最小修正。
6. 重跑最小复现、原始场景和相关回归；删除临时 instrumentation。

### 产物

- 新行为的 red→green 记录，或故障的复现与根因证据。
- 回归测试、最小修正和相关验证结果。
- 已排除假设、仍未排除假设和环境限制。

### 质量门

- 测试通过 public interface 验证调用者关心的行为。
- 测试没有复算实现逻辑，也没有依赖不稳定的内部调用次数。
- 根因结论能预测实验结果，不是知道结果后的解释。
- flaky 问题有稳定性证据；「暂时没再发生」不算修复。

### 停止与恢复

- **停止：** 无法建立 red-capable loop；必须访问生产或真实数据；同一问题连续三轮验证仍失败。
- **恢复：** 请求脱敏 artifact、隔离复现环境或明确的临时 instrumentation 授权；重新审查架构、数据流和状态管理后提出新假设。

## 阶段 8：PostgreSQL 与 migration 专项

### 前置条件

- 仓库证据确认使用 PostgreSQL，并已启用 `postgresql-migrations` 模块。
- 已确认 migration 工具、schema 规范源、目标环境、执行顺序和项目恢复策略。
- 规格已决定数据模型和兼容要求。

### 动作

1. 搜索受影响表、约束、索引、查询路径、模型、fixture 和并行部署兼容要求。
2. 在改动前写明 forward、rollback 或替代恢复方案，并说明不可逆步骤和潜在数据损失。
3. 优先 expand–migrate–contract：先兼容扩展，再迁移读写和数据，确认无残留后收缩。
4. 对删除、重命名、类型收窄、全量回填、长锁或约束即时校验，先请求明确授权。
5. 使用项目已有生成流程创建 migration；不要手改要求自动生成的产物。
6. 在项目已有临时数据库、容器或 fixture 上验证升级、应用行为和恢复路径。
7. 只有授权范围明确时才使用数据库 MCP；先只读 schema 与计划信息，真实写入和生产连接逐项确认。

### 产物

- 可审查的 migration、应用兼容改动和相关测试。
- forward / rollback 或不可逆理由。
- 锁、数据规模、耗时和部署顺序的事实与未知项。
- 隔离环境验证记录。

### 质量门

- migration 失败会显式暴露，不用吞错或「存在即跳过」掩盖漂移。
- 新旧应用与中间 schema 的兼容性已按实际部署方式验证，或明确标为未验证。
- 索引和查询改动绑定实际查询路径；执行计划结论仅来自对应环境实测。
- 没有连接、修改或迁移未经授权的真实数据库。

### 停止与恢复

- **停止：** 生产数据规模、锁风险或部署顺序未知；恢复路径不成立；操作需要真实凭据或生产写入。
- **恢复：** DBA 或负责人提供证据和授权；改为分阶段兼容方案；在代表性隔离数据上重新验证。

## 阶段 9：前端视觉质量专项

### 前置条件

- 改动影响页面、组件、样式、交互、响应式布局或可访问性。
- 已启用 `frontend-visual-quality` 模块。
- 已确认目标页面、用户流程、viewport、主题和浏览器范围，以及界面类型、主/次/风险操作、输入方式和同屏比较基准。

### 动作

1. 查找并复用已有 design tokens、组件、字体、图标、spacing、颜色和动效约定；先确认界面类型、主/次/风险操作、输入方式和同屏比较基准。
2. 列出任务涉及的 loading、empty、error、disabled、success、focus、overflow 和 reduced-motion 状态。
3. 实现清晰的信息层级和主操作路径，不为单页引入新的设计系统。
4. 验证静止态层级、通用图标语义、icon-only 控件的 accessible name 和交互命中区；核心语义不得只依赖 hover、tooltip、颜色或动效。
5. 运行相关组件或端到端测试；共享组件、路由或构建配置变化时追加已有 lint、typecheck 和 build。
6. 在实际浏览器中检查目标 viewport 和关键交互状态。记录页面、viewport、输入步骤、同屏比较基准和结果；实际渲染后比较相对尺度、视觉重量和信息密度。
7. 视觉调整后复验文字可读性、可见 focus、对比度、命中区和状态语义。
8. CLI 没有可用浏览器、截图或视觉回归工具时，记录未验证范围；不依赖 Codex Desktop 右侧面板。可以把浏览器状态检查分配给独立 Subagent，但必须提供页面、viewport、fixture 和验收清单；父 Agent 复核重要截图或复现步骤。

### 产物

- 用户可见行为和状态的实现。
- 浏览器检查记录、必要截图或视觉回归结果。
- 组件 / E2E 测试及相关静态检查结果。
- 未覆盖的浏览器、viewport 或数据状态。

### 质量门

- 目标窄屏和宽屏没有截断、重叠、意外横向滚动或不可达操作。
- 键盘可操作，focus 可见，状态反馈不只依赖颜色。
- loading、empty、error 和 disabled 等实际涉及状态已检查。
- 没有实际启动页面和查看渲染结果时，不报告视觉质量通过。

### 停止与恢复

- **停止：** 缺少品牌或交互决定；页面只能依赖真实用户数据或生产服务打开；需要新增组件库、字体或图标依赖。
- **恢复：** 用户确认设计方向；提供脱敏 fixture 或本地 stub；取得依赖变更授权并更新规格后继续。

## 阶段 10：双轴代码审查

### 前置条件

- 已固定审查范围，能够明确列出 changed files 或 diff。
- 规格、验收条件和适用的项目规则可定位。
- 实现者已完成自审和直接验证。

### 动作

1. 调用 `two-axis-code-review`。
2. 独立执行两个轴：
   - **Standards：** 正确性、安全、兼容性、项目惯例、测试和维护风险。
   - **Spec：** 遗漏、部分实现、错误实现、scope creep 和验收覆盖。
3. 大 diff 优先由两个只读 Subagent 分别审查两个轴。审查者不得直接修改实现。
4. 只读核对 `Ablation evidence` 与实际 diff；Spec / Standards 两轴保持不变，不自动修复。
5. 每个 finding 写明严重度、文件或位置、触发条件、影响和最小修正方向。
6. 修复 finding 后重跑受影响的测试和审查检查。不能用更新规格掩盖实现偏差，除非需求确实改变并经用户确认。
7. PR 评论、issue 创建或远程状态修改需要单独外部写入授权。

### 产物

- Standards findings 与 Spec findings 两份独立结果。
- 已修复 finding、接受的风险和未验证范围。
- 修复后的新鲜验证证据。

### 质量门

- 所有 changed behavior 都在两个轴上检查。
- finding 能定位、复现并追溯到代码与规则或需求证据。
- 没有 finding 时明确写 `No findings`，并列出未验证范围。
- 审查者没有因「代码质量好」忽略规格偏差，也没有因「功能能用」忽略安全或兼容问题。

### 停止与恢复

- **停止：** 无法确定 diff；规格不可用；finding 需要改变需求；审查依赖缺失的运行环境。
- **恢复：** 固定 ref 或工作区范围；由用户补充验收条件；更新规格后重审；建立隔离环境执行缺失验证。

## 阶段 11：交付与外部动作

### 前置条件

- 所有计划切片已完成，或剩余项已明确移出本次范围。
- 重要 review finding 已处理或由负责人明确接受。
- 验证输出是本轮新鲜结果，且没有被截断。

### 动作

1. 检查最终 diff，只保留任务相关改动。
2. 运行与风险相称的最终验证组合：目标测试、相关回归、lint、typecheck、build、页面检查或 migration smoke。
3. 检查生成文件来源、临时 artifact、debug code、unused 和文档一致性。
4. 形成验证矩阵：验收项、执行命令或检查、结果、证据层级、未验证原因。
5. 最终报告如实列出删减、保留、验证和 Limitations；不把 contract-only 或静态检查写成真实 Agent 运行。
6. 汇报结论、实际改动、原因、验证结果、未完成事项和残余风险。
7. 默认在此结束。只有用户针对本次任务明确要求时，才进入 commit、push、PR、发布或部署。
8. 外部动作前重新确认目标仓库、分支、环境、接收方、回滚方式和授权范围；动作后读取实际状态，不把请求已发送当作部署成功。

### 产物

- 可审阅代码和文档。
- 最终验证矩阵与实际输出摘要。
- 未完成项、未验证项和残余风险。
- 若另行授权，外部系统返回的可核验结果。

### 质量门

- 完成声明满足本 SOP 的完成定义。
- dry-run、fixture、本地 smoke、只读检查和真实副作用没有混为同一验证层级。
- 未默认 commit、push、merge、发布或部署。
- 外部动作的对象和结果均来自实际返回，而不是理论预期。

### 停止与恢复

- **停止：** 关键测试失败；输出被截断；部署或生产写入没有授权；回滚条件不明。
- **恢复：** 修复失败并重新执行完整检查；缩小输出范围重新读取；取得对象级授权并演练恢复路径。

## 阶段 12：规则演进与人工晋升

### 前置条件

- 出现了测试失败、用户纠正、返工、重复故障或有证据的流程缺陷。
- 该经验可能影响未来多个任务，而不是一次性任务流水账。

普通成功不自动触发规则写入。

### 动作

1. 在 `.agents/memory/candidates.jsonl` 追加待审候选。每行只含八个非空字符串字段：`id`、`observation`、`evidence`、`scope`、`destination`、`conflicts_and_risks`、`expiry_signal`、`status`；`status` 固定为 `candidate`。不要写 secrets、PII 或原始聊天。
2. 判断正确载体：
   - 跨多数任务稳定的行为进入用户级短常驻内核候选。
   - 项目长期事实进入项目画像、就近规则或既有开发记录候选；项目 core 只保留路由。
   - 多步骤判断流程进入 skill 候选。
   - 路径或技术栈局部规则进入模块候选。
   - 必须确定执行的限制进入 hook、permissions 或 CI 候选。
   - 文件分类、frontmatter、草稿/临时/归档等约束仅在仓库采用时进入 `file-document-governance` 或项目局部规则，不晋升为跨项目常驻规则。
3. 使用 `writing-for-agents` 的 Audit 模式检查规则是否改变 Agent 决策、是否位于正确层级、是否有足够证据，并给出 retain、rewrite、move、delete 或 needs-evidence 结论。只有用户明确要求治理项目画像或 Memory 时，才分别显式调用 `project-profile` 或 `memory-governance`。
4. 候选先进入待审池。不要在产生失败的同一会话中自动晋升为正式规则。
5. 人工审阅候选的证据、适用范围、平台差异和回滚方式。
6. 在隔离目录和代表性 eval 任务中比较变更前后行为。没有真实模型运行时，只报告结构验证，不声称质量提升。
7. 人工批准后修改 canonical 单一事实源。先运行 `render-templates` 审查完整目标映射，再执行 `render-templates --apply` 并审查仓库 diff，最后运行 `validate`；不要直接编辑平台快照的共享块。
8. 保留可回滚版本；被证伪、过时或造成冲突的规则应降级、收窄或删除。

### 产物

- 待审候选记录，或经批准的规范化规则 / skill / hook / CI 变更。
- 证据、评测结果、批准记录和回滚说明。
- 同步后的平台适配文件和结构校验结果。

### 质量门

- 规则解决的是可复现问题，并有反例边界。
- 一个含义只存在一个规范化来源；平台文件没有手工分叉。
- 候选不包含 secrets、PII、一次性路径或未核实平台能力。
- 人工批准和验证发生在晋升之前。

### 停止与恢复

- **停止：** 只有单次偶然现象；证据不足；候选与现有规则冲突；需要真实模型付费评测或会修改真实用户配置。
- **恢复：** 收集第二个独立实例或可复现测试；解决冲突并收窄范围；取得评测或安装授权后在隔离环境继续。

## 任务状态模板

长任务可用以下最小状态记录，避免依赖聊天上下文：

```markdown
## Objective

## In scope / Out of scope

## Facts / Decisions / Assumptions / Open questions

## Acceptance criteria and evidence

## Current slice

## External-effect authorization

## Verification run / blocked / not run

## Next safe action
```

状态记录不得包含 secrets、认证信息、PII 或大段工具输出。恢复任务时，先核对状态记录与当前工作区是否仍一致，再执行 `Next safe action`。
