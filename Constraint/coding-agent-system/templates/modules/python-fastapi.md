# Python / FastAPI 模块

## 触发范围

当任务涉及项目已存在的 Python 或 FastAPI 代码时启用。先通过 Python 项目配置、依赖声明、应用入口、路由或测试确认技术栈，不因目录名或单个 import 推断整个项目。

## 先发现项目事实

- 从项目配置、lockfile、容器和 CI 确认 Python 版本、依赖管理方式与运行环境，不切换现有工具。
- 确认 FastAPI 及数据验证库的实际版本、应用创建方式、依赖注入、生命周期和 sync/async 边界。
- 从项目配置和文档确认 test、lint、format、typecheck、migration 与启动命令。
- 查找现有包布局、配置加载、日志、异常映射、数据库 session 和测试 fixture 约定。
- 确认目标是否是生成文件，以及接口契约是否由 OpenAPI、schema 或其他源文件生成。

## 最小质量门槛

- 先测量再优化：性能、内存、并发或延迟改动先取得项目相关的基线、瓶颈证据和验收指标；没有测量时不把猜测当优化结论。
- 沿用现有类型和数据模型，不为局部改动引入第二套验证、配置或依赖注入方案。
- 不在 async 路径中加入未经评估的阻塞 I/O；不把同步实现机械改成异步。
- 在入口边界验证外部数据，内部失败应保持可追踪；不要捕获宽泛异常后静默返回成功或空值。
- 保持 API 状态码、错误结构、事务边界和向后兼容要求；契约变化需要对应测试或文档证据。
- Bug 修复覆盖复现用例、错误路径和直接相关边界；测试使用项目现有 fixture 与隔离策略。

## 验证命令选择

1. 从项目配置、脚本、CI 或开发文档选择现有命令，不假定某个测试或环境工具存在。
2. 优先运行目标测试；公共模型、依赖、路由或配置变化时追加项目已有的 lint、typecheck 与集成检查。
3. 使用仓库已确认的解释器和依赖管理入口，不全局安装工具，不无依据升级依赖。
4. 若服务依赖外部系统，优先使用项目已有 fixture 或隔离环境；真实外部调用仍需明确授权。
