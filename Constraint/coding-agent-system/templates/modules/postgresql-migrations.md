# PostgreSQL Migration 模块

## 触发范围

当任务涉及项目已存在的 PostgreSQL schema、migration、SQL、索引、约束、数据回填或数据库访问层时启用。没有仓库证据时，不假定数据库、migration 工具或部署拓扑。

## 先发现项目事实

- 从依赖、配置、migration 目录和 CI 确认数据库类型、migration 工具、命名规则、当前依赖关系和执行入口。
- 确认 schema 的规范源、目标环境、兼容窗口、部署顺序、事务支持和项目既有回滚策略。
- 查明受影响表、约束、索引、查询路径、数据规模与锁风险；无法从仓库确认的生产事实标为未知。
- 搜索应用读写路径、序列化模型、测试 fixture、种子数据和并行部署时的新旧代码兼容要求。
- 确认仓库是否允许生成 migration；不得手改工具生成且项目要求再生成的产物。

## 最小质量门槛

- 在改动前写清 forward、rollback 或其他恢复方案，并说明可能的数据损失和不可逆步骤。
- 优先兼容式、分阶段变更。删除、重命名、类型收窄、全表回填、长锁或约束即时校验必须显式评估并请求授权。
- migration 应可重复审查，失败应显式暴露；不要用吞错或“存在即跳过”掩盖状态漂移。
- 索引和查询改写必须绑定实际查询路径；执行计划、锁行为和耗时结论只有在对应环境实测后才能作为事实。
- 未获明确授权，不连接、修改或迁移真实数据库。

## 验证命令选择

1. 从仓库文档、任务脚本或 CI 确认 migration 状态、生成、升级、降级和测试命令。
2. 优先在项目已有的临时数据库、容器或 fixture 上验证从前一 schema 到目标 schema，再验证恢复路径或记录不可逆理由。
3. 运行直接相关的模型、repository 和集成测试；跨版本部署时验证新旧应用与中间 schema 的兼容性。
4. `EXPLAIN ANALYZE` 会执行语句；仅当环境隔离、只读或可恢复，且项目流程允许时才使用。需要真实数据或生产连接时停止并请求授权。
