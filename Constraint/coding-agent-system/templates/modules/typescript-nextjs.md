# TypeScript / Next.js 模块

## 触发范围

当任务涉及项目已存在的 TypeScript、React 或 Next.js 代码时启用。常见证据包括 `package.json`、TypeScript 配置、Next.js 配置、路由目录或相应源文件；文件名本身不是充分证据，仍需核对依赖和调用关系。

## 先发现项目事实

- 从 lockfile、`packageManager` 字段和仓库文档确认包管理器，不自行选择或切换。
- 从依赖清单和配置确认运行时、框架、TypeScript 版本以及项目实际使用的 router、渲染和数据获取模式。
- 从 scripts、CI 和开发文档确认 lint、typecheck、test、build 与生成命令。
- 查找现有目录边界、路径别名、组件模式、错误处理、状态管理、样式方案和测试约定。
- 确认目标文件是否由代码生成，及其规范源文件和生成流程。

## 最小质量门槛

- 保持现有 server/client 边界、路由模式和数据流；除非任务要求，不迁移框架模式或新增状态层。
- 新增或修改的公开类型应表达真实不变量，不用 `any`、类型断言或宽泛兜底掩盖未知数据。
- 在系统边界验证不可信输入，沿用项目现有 schema、错误和响应约定。
- 组件和工具函数保持单一职责；仅在项目已有多个真实调用方时提取共享抽象。
- 行为变化覆盖关键路径、错误路径和直接相关边界；不为通过测试修改无关快照或断言。

## 验证命令选择

1. 从项目 scripts、任务运行器或 CI 选择针对变更路径的最小检查。
2. 优先运行相关测试和类型检查；共享模块、路由、构建配置或渲染边界变化时再扩大到 lint 与 build。
3. 使用仓库已确认的包管理器执行原有命令，不把示例命令、全局工具或猜测的 script 名当作事实。
4. 无法运行时记录缺失的命令、依赖或环境，并用可行的静态检查补充，但不得声称等价通过。
