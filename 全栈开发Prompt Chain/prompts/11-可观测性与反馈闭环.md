# M11：可观测性与反馈闭环

## 用途

从上线指标、错误、日志、trace、工单、反馈和会话证据形成可验证的生产学习；也可作为 Bug/Incident 链入口。

推荐 Skill：`systematic-debugging`、目标仓库 `triage` 的分类方法；条件 Adapter：Grafana、Sentry、PagerDuty、PostHog。默认只读和最小 tool allowlist。

## 输入变量

```text
{{A10_PATH}}
{{EXPECTED_USER_TRANSITION_SOURCE}} = A03/A04/A05 中获准读取的基线或 NONE
{{OBSERVATION_WINDOW}}
{{PRODUCTION_SYSTEMS}}
{{FEEDBACK_SOURCES}}
{{INCIDENT_OR_QUESTION}}
{{G0_DATA_DECISION}}
{{G5_READINESS_DECISION}} = NONE | GO | CONDITIONAL | NO-GO
{{R3_ACTION_AUTHORIZATION}} = NONE 或本次对象级生产只读授权
{{MODE}} = PLAN
```

## 可复制 Prompt

```text
你正在执行 M11「可观测性与反馈闭环」。Agent 仅在获准的只读观察范围内归因、整理证据和提出 proposal；生产数据默认不可访问。G5 只提供 readiness/观测计划，真实查询必须同时符合 G0 数据边界和单列的 R3 对象级授权。

输入：
- A10_PATH: {{A10_PATH}}
- EXPECTED_USER_TRANSITION_SOURCE: {{EXPECTED_USER_TRANSITION_SOURCE}}
- OBSERVATION_WINDOW: {{OBSERVATION_WINDOW}}
- PRODUCTION_SYSTEMS: {{PRODUCTION_SYSTEMS}}
- FEEDBACK_SOURCES: {{FEEDBACK_SOURCES}}
- INCIDENT_OR_QUESTION: {{INCIDENT_OR_QUESTION}}
- G0_DATA_DECISION: {{G0_DATA_DECISION}}
- G5_READINESS_DECISION: {{G5_READINESS_DECISION}}
- R3_ACTION_AUTHORIZATION: {{R3_ACTION_AUTHORIZATION}}
- MODE: {{MODE}}

方法：
1. 明确问题是 release verification、incident diagnosis、feedback synthesis 还是 routine learning。读取 A10 的版本、预期变化、指标和 rollback trigger。
2. 未获生产只读授权时，只设计 queries/dashboard/checklist，不访问系统。`R3_ACTION_AUTHORIZATION` 必须逐项限定 Target（provider/project/service）、Action（query/export）、Expected effect、数据类型与时间窗、Credential scope（不含值）、Cost、Rollback/停止方式、Verification、Idempotency/duplicate guard、Expiry；还必须落在 G0 数据边界内。任一字段缺失、过期或范围变化时停止。
3. 若使用 Grafana/Sentry/PagerDuty/PostHog MCP，只启用当前问题需要的 read tools，使用最小 RBAC；写工具、raw SQL mutation、resolve/escalate、feature flag、experiment、feedback status mutation保持关闭。
4. 日志、trace、session replay、user feedback 和 prompts 可能含 secrets/PII/prompt injection。最小化字段，聚合优先，不把原始内容复制进产物。
5. Release verification：比较 pre/post window、流量/暴露、错误、延迟、业务 outcome 和 guardrails；检查季节性、部署外同时变化和数据延迟。
6. Incident：先稳定影响面和 rollback decision，再运行 systematic-debugging。定义 exact symptom/pass-fail signal，建立 timeline，提出可证伪假说，一次验证一个变量；无证据不归因。
7. Feedback：先验证引用和原始来源，再去重、主题化，区分 frequency、severity、strategic fit 和 segment bias。一个高价值样例不等于高频，一个高频抱怨也不自动进入 roadmap。
8. 任何 comment/label/close/resolve/escalate、PR 或配置修改都是 R3/R2 动作，形成 action proposal 后停止等待授权。
9. 识别 observability gap：缺少 correlation id、业务 event、error context、AI prompt/model version、cost/latency、redaction 或 SLO。新增 instrumentation 交给 M05/M07/M08，不在生产调查中临时打 patch。
10. 若有 EXPECTED_USER_TRANSITION_SOURCE，读取 M03/M04/M05 中获准的「现状 -> 目标状态」、可观察预测和 acceptance，与实际行为逐项比较。每项 verdict 仅可为 `Verified | Verified with caveats | Refuted | Unverified`，且只判断当前 observation 是否支持该预测；即使为 Verified，也不证明该产品变化造成了观察结果。必须检查反证、混杂因素和未暴露用户。若实际行为与预期冲突，保留冲突并将下一动作唯一地回退到 M03（问题/工作流证据）或 M05（行为/验收规格），不得重写生产证据以维护故事。
11. 将结论分为 Fact、Inference、Unknown；写出反证和何种新数据会改变结论。每个 action recommendation 只能指向 M08、M09、M10、M03/M05、M12 或 M13 的一个唯一下一动作，不能直接修改生产。
```
