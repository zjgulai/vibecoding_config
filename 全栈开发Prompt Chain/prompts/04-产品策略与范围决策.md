# M04：产品策略与范围决策

## 用途

把机会和问题证据转成明确的产品选择、成功指标、范围与取舍，完成 G2。

推荐 Skill：`product-discovery` 的决策模式、`domain-modeling`；外部可参考 PM Skills 的 strategy red-team、pre-mortem、north-star/metric tree。

```text
{{A02_PATH}}
{{A03_PATH}}
{{BUSINESS_CONSTRAINTS}}
{{TIME_HORIZON}}

{{MODE}} = PLAN
```

## 可复制 Prompt

```text
你正在执行 M04「产品策略与范围决策」，只形成决策，不实施。

输入：
- A02_PATH: {{A02_PATH}}
- A03_PATH: {{A03_PATH}}
- BUSINESS_CONSTRAINTS: {{BUSINESS_CONSTRAINTS}}
- TIME_HORIZON: {{TIME_HORIZON}}
- TEAM_CAPACITY: {{TEAM_CAPACITY}}
- MODE: {{MODE}}

授权边界：`MODE=PLAN` 只在回复中生成 A04 内容或拟落盘内容预览，不写任何文件。只有 `MODE=APPLY`，且适用的 G3 决定、G4 本地写入授权与精确输出文件范围一致时，才可持久化；不得把策略批准或输出文件名解释为写入许可。

步骤：
1. 验证 A02/A03 状态、来源和新鲜度。G1 未通过时停止产品承诺，只提出补证据路径。
2. 写清目标用户、核心 job、价值变化和为何现在。把「现状 -> 目标状态」登记为价值转变假说，分别写支持证据、反证、适用用户/情境边界和可观察结果；不得因故事完整就把转变当作已验证价值。不要把功能列表当策略。
3. 提出 2–3 个真正不同的策略选项，包括“不做/继续现状”基线。每个选项比较用户价值、可达性、风险、成本、可逆性、第二序效应和证据缺口。
4. 从第一性原理和系统思维检查：增长/留存反馈环、供应/需求约束、激励错位、滥用、隐私、支持成本、运营瓶颈和技术杠杆点。
5. 做反向分析与 pre-mortem：六个月后失败，最可能的可观测原因是什么？哪些先导指标会提前出现？
6. 定义一个主要 outcome、少量 input/guardrail metrics；写公式、数据来源和不可接受的副作用。没有数据管道时标记为待建设，不伪造 baseline/target。
7. 确定 MVP 是最小可验证价值链，不是最少页面。明确 non-goals、手工运营边界和退出条件。
8. 对定价、权限、数据、AI 自主性、内容/安全等高影响选择单列待确认项。
9. 给出推荐但不替用户做重大产品决定。用户批准后把状态改为 approved；仅有 Agent 推荐时保持 draft。
```
