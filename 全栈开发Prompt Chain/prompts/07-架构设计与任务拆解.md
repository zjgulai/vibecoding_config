# M07：架构设计与任务拆解

## 用途

从已确认规格形成最小架构决定、接口/seam 和无环垂直切片。默认不创建远程 tickets。

推荐 Skill：`codebase-design`、`vertical-ticketing`；大型模糊工程可参考 `wayfinder`，但只生成本地 decision map。

```text

输入：
- A01_PATH: {{A01_PATH}}
- A05_PATH: {{A05_PATH}}

- TICKET_DESTINATION: {{TICKET_DESTINATION}}

授权边界：`MODE=PLAN` 只在回复中生成 A07 内容、decision map 或 tracker preview，不写任何文件。只有 `MODE=APPLY`，且适用的 G3 决定、G4 本地写入授权与精确文件范围一致时，才可持久化本地产物；tracker 等外部写入仍需独立对象级授权。

方法：
1. 先验证规格状态并读取实际代码结构、调用图、数据流、tests、依赖和既有 patterns。不存在代码库时写目标架构假设，不伪称现有实现。
2. 若 codebase-design 已安装，在 interface、seam、adapter、locality 或 testability 需要判断时加载；用户明确要求拆票时加载 vertical-ticketing。
3. 识别必须决定的架构点与可延期点。使用 deep module 原则：尽量让复杂性藏在稳定、小接口后；但不要为了模式而创建没有调用方的 abstraction。
   - Shared transform 只有在同一份 approved spec 面向至少两个真实目标、且这些目标确实共享同一段语义时才可启用。此时才允许设计 `canonical source -> validated intermediate contract -> shared transform -> target adapters`，并定义共享不变量、reference contract、各目标能力/成熟度、允许差异和共享层变更的影响半径；“未来也许有第二目标”或单目标平台差异都不满足此门槛。
   - Target adapter 与 shared transform 分开判定：多目标可因目标原生差异使用 adapter；单目标只有在存在不可忽略、且不能由简单配置表达的平台差异时才可使用 adapter。任何 adapter 在进入实施前都必须先命名可运行的 native validator、适用输入与判定标准；没有 native validator 就保留为未批准方案，不创建 adapter。
   - 单目标 adapter 不自动触发 shared transform、validated intermediate contract、reference parity 或目标矩阵；只记录该平台差异、adapter 边界和 native validator。不得只为“架构感”增加中间层；不满足任一条件时明确记录 `Shared transform: Not applicable` 与 `Target adapter: Not applicable`。
4. 对每个重大设计至少比较 2 个可行选项，包括延续现状；评估正确性、演进、可测试性、可观测性、安全、性能、运维和可逆性。
5. 明确 data ownership、transaction/idempotency、authn/authz、error semantics、timeouts/retries、compatibility 和 migration path。AI 功能还要定义 provider boundary、fallback、eval seam、成本和数据外传边界。
6. G3 未通过前不把高影响方案写成实施指令。需要 dependency/schema/public API 变化时列出影响、rollback/repair 和验证。
7. 按用户可观察行为拆垂直 slices；每个 slice 贯穿需要的 UI/API/data/test，完成后保持系统可用。不要只按 frontend/backend/database 横切。
8. 用户可见 ticket 必须从 A05/A06 追溯视觉约束、已批准例外、目标页面、viewport、状态、复用的 token/component/icon source 和同屏验证方法；本阶段不重新做视觉决策，缺失或矛盾项保持 blocker/open question。新增组件或图标 dependency、跨 design system、公共 UI API 变化仍分别受 G3 决策和 G4 精确写入授权约束；G4 不代替 dependency 或外部动作授权。
9. 每个 ticket 写 Deliverable、Acceptance、Files/Interfaces、Blocked by、Verification、Out of scope、Risk。依赖只表示真正不能开始的阻塞边；检查 DAG 无环。
10. 只在文件和状态不重叠时标记 parallelizable。共享接口由单一前置 slice 负责，父 Agent 保留最终集成。
11. 架构选项和 slice/DAG 初稿形成后、请求 G3/G4 前，逐项检查本轮新增的 abstraction、interface、seam、adapter、layer、dependency、config 和 ticket；能删或延后则 remove/defer，保留项必须追溯当前 requirement、invariant、failure mode 或 risk。不得借此绕过 G3，或抹去安全、兼容、migration、recovery、observability/test seam。
12. 默认只在回复中输出本地产物内容，不落盘。tracker-preview 只生成将创建的 Issue 预览、幂等键/去重策略和 dependency 映射；不执行本地或外部写入。

每个准备进入 M08 的 slice 都要形成 Agent-ready module pack：`Scope`、`Authoritative entry points`、`Reads/Writes`、`Existing feedback commands`、`Mocks/dependencies`、`Interfaces and invariants`、`Failure/recovery`、`Integration owner`、`Not authorized`。每项必须来自仓库证据、A05/A06/A07，或明确写 `Unknown`；该包不是独立 Gate 或长期 profile。
```
