# 全栈开发 Prompt Chain Implementation Plan

> **For agentic workers:** 本计划采用文件级并行起草、主线程统一术语与独立审查。当前目录不是 Git 仓库，因此不执行 commit/worktree 步骤；以文件哈希、结构检查、链接检查和双人审阅替代 Git diff gate。

**Goal:** 产出一套可直接复制使用、证据可追溯、覆盖 AI 产品从机会发现到上线自迭代的模块化 Skill 审计与 Prompt Chain。

**Architecture:** 交付物分为四层：事实层记录目标仓库与外部候选证据；模型层定义生命周期、模块和 Skill 关系；执行层提供模块工作流与审批门；使用层提供平台中立、输入输出可串接的 Prompt。`report-source.md` 是来源与主张的唯一研究账本，其他文档通过固定链接引用它。

**Tech Stack:** Markdown、Mermaid、GitHub 固定 commit 链接、Shell/Python 只读验证脚本。

## Global Constraints

- 研究基线固定为 `vinvcn/mattpocock-skills-zh-CN@9fe7e7a3bb352851b986725bab1c7cfb17610a97`。
- 区分 29 个公开稳定 Skill、6 个 in-progress Skill、1 个仓库内部 Skill；不得把三类混为同一稳定等级。
- 明确区分事实、推断、不确定项；stars 只作为生态关注度快照，不作为质量证明。
- 外部候选采用固定 commit、逐 Skill、逐许可证评估；不建议无审计地整包安装。
- 所有可能 commit、push、建 Issue、改标签、写 secret、部署、操作生产或发送外部消息的步骤必须放在显式审批门之后。
- Prompt 不要求模型披露隐藏 Chain of Thought；用证据、假设、备选方案、反证和决策理由替代。
- Codex、Claude Code、DeepSeek Harness 是平台适配对象；Cursor 只提供规则组织与上下文治理思路，不作为第四平台。
- 文档正文使用中文；Skill identifier、文件名、命令、API 和产品名保留英文。
- Prompt 模块必须有确定的输入契约、输出契约、完成标准、停止条件、下一节点和失败回退。
- 不创建自动执行器，不安装候选 Skill，不调用真实 tracker、生产系统、部署系统或付费模型。

## 2. 研究问题

1. 目标仓库每个 Skill 的真实功能、调用主体、输入、输出、依赖、直接副作用和生命周期位置是什么？
2. Skill 之间有哪些直接调用、共享 primitive、替代关系和阶段交接关系？
3. 原仓库能覆盖 AI 产品生命周期的哪些部分，遗漏了哪些部分？
4. 高关注度或第一方候选在哪些缺口上提供了更好的方法或工具？
5. 哪些内容应作为核心能力、补充能力、条件适配器、替代方案或排除项？
6. 如何让每个 Prompt 的输出成为下一 Prompt 的可验证输入，而不是依赖长对话记忆？

## 3. 证据等级

| 等级 | 定义 | 允许支持的结论 |
|---|---|---|
| E1 | 固定 commit 的 `SKILL.md`、脚本、配置、许可证或官方文档 | 功能、调用、写入行为、版本、许可证等事实 |
| E2 | 官方 README、GitHub API、维护者文档或发布记录 | 维护状态、安装方式、平台能力 |
| E3 | 交叉仓库对照、静态依赖图、结构化比较 | 关系、覆盖、缺口与冲突 |
| E4 | 专家判断与风险推断 | 候选等级、整合建议；必须标明是判断 |
| E5 | 实际运行、测试或生产证据 | 本项目没有执行候选 Skill，因此不得声称达到此等级 |

## 4. 评测维度

每个外部候选从以下十个维度评估：

1. 生命周期相关性。
2. 触发条件是否清晰。
3. 输入输出契约是否明确。
4. 能否与其他 Skill 组合。
5. 是否要求验证和新鲜证据。
6. 是否有危险或外部副作用。
7. Codex、Claude Code、DSH 的可移植性。
8. 维护活跃度和固定版本可用性。
9. 许可证与复制边界。
10. 是否有 benchmark、测试或实际运行证据。

采用以下结论标签：

- `Core`：默认流程的核心方法。
- `Supplement`：补强现有 Core，不替代。
- `Alternative`：同一职责的另一套完整方法。
- `Adapter`：只在项目已使用相应平台或工具时启用。
- `Niche`：适用面窄，但在特定栈中有价值。
- `Exclude`：仅作反例或研究来源，不建议纳入执行基线。

## 7. 完成标准

只有同时满足以下条件才可声明完成：

- 目录和预期文件全部存在。
- 目标仓库 36 个 Skill 均有功能、调用、输入/输出、关系和风险说明。
- 生命周期从需求调研覆盖到上线、反馈、增长和自进化。
- 每个模块至少有一个推荐 Skill 组合；缺少成熟候选的模块明确写出证据缺口。
- 端到端 Prompt Chain 可以只依赖上一步产物继续，不要求保留完整聊天上下文。
- 所有真实副作用均有审批门；只读研究和写入执行明确分离。
- 来源账本可以追溯关键事实，且没有把未运行的候选描述为实测有效。

## 8. 计划自审

- Spec coverage：用户五项要求分别由 Tasks 1–4 覆盖，落盘与验证由 Task 5 覆盖。
- Placeholder scan：本计划不含 `TBD`、`TODO` 或“稍后补充”；Prompt 中出现的 `{{VARIABLE}}` 将被明确定义为用户输入变量。
- Interface consistency：M00–M13 与 A00–A13 一一对应；`A13-retrospective.md` 是完整链最终产物，也可反向触发下一轮 M02/M03。
- 环境偏离：当前目录不是 Git 仓库，无法执行 `writing-plans`/`subagent-driven-development` 默认的 commit、worktree 和 Git diff review；改用文件级隔离、哈希和独立内容审查。
