# 故事线驱动与编译式交付模式

## 1. 结论

本轮不引入新的生命周期、Gate、artifact 或缩写。可取的方法是把三类来源分别放到现有控制面的不同层：

- 用 AI 产品故事线回答「为什么做、为谁做、价值如何被观察」，形成贯穿 A02–A12 的叙事约束；
- 用编译器工程回答「同一意图怎样稳定投影到不同模型、平台和产品目标」，把 A05 视为 canonical specification，把共享处理与目标适配分开；
- 用 fable-method 回答「一次工作怎样从模糊请求收敛为有证据的结果」，强化完成定义、命名验证、陷阱样例、独立判定和失败保留；
- 所有新增方法都投影到既有 `M00–M13`、`A00–A13`、`G0–G6` 与 Control Contract，不建立第二套控制面。

目标链路为：

```text
真实问题与用户故事
  → canonical specification（A05）
  → shared transforms（A06/A07/A08 的共享决策与实现）
  → conditional target adapters（多目标差异，或单目标中不能由简单配置表达的平台差异）
  → native validators（A08/A09）
  → release / observation（A10/A11/A12）
  → 复盘与能力候选（A13）
  ↺ 新证据回到最小正确上游模块
```

这是一种交付组织方式，不是代码生成器设计，也不要求项目采用 F#、编译器或 fable-method 的原始命令。

## 4. 模型配置侧的整合

### 4.1 常驻内核保持短小

用户级 AGENTS/CLAUDE 配置只应新增或强化以下稳定语义：

1. 先识别任务形态：研究、规格、原型、实现、调试、审查、发布准备或运行观察。
2. 对非琐碎任务命名 `Definition of Done` 和实际可运行的 verification；不能运行时明确写 `unverified`。
3. 区分 canonical behavior、shared concern 和 target-specific concern；多目标工作先查相邻 adapter 与兼容面。
4. 事实、推断、设计决定和未验证项分开；完成声明必须基于观察，而不是计划、生成或单次工具成功。
5. 设计或实现后做消融：去掉不能追溯到当前 requirement、invariant、failure mode 或 risk 的抽象、adapter、测试和 guardrail。

详细步骤留在 Prompt、Skill 或项目文档，避免把三份来源的全文堆入常驻上下文。

### 4.2 模型路由采用能力卡，不采用品牌教条

每个可选模型记录一张可更新的能力卡：

| 字段 | 要求 |
|---|---|
| Task shapes | 已观察适合的研究、规划、代码、视觉、审查或长上下文任务 |
| Context limits | 可用上下文、压缩行为、仓库读取能力与已知丢失模式 |
| Tools and authority | 实际可用工具、sandbox、网络、凭据和外部副作用边界 |
| Named verifications | 该任务能运行的测试、fixture、browser、judge 或人工检查 |
| Failure signatures | 越权、过度抽象、测试迎合、目标 adapter 漂移、伪完成等已观察模式 |
| Calibration evidence | 同任务、同输入、同环境的 baseline/candidate 结果，含 null/failure |
| Expiry | 模型、harness、工具或项目边界改变时失效 |

路由顺序是「任务形态 → 风险与授权 → 所需工具和上下文 → 命名验证 → 模型」。模型名只在最后选择。没有校准证据时，结论写为假设；不得把会议经验转换为固定的 Claude/Codex/Gemini/DeepSeek 角色表。

### 4.3 交接保持 artifact-first

不同模型或 Agent 的交接继续使用 A00–A13 与 Control Contract。交接至少包含：权威输入、已决定与未决定事项、允许范围、目标 adapter、命名验证、原始证据位置、失败记录、未验证范围和唯一下一安全动作。交接文档不传递隐含权限，也不要求保存隐藏思维链。

## 6. 编译式交付的执行契约

### 6.1 Canonical specification

A05 至少明确：用户可观察行为、领域词汇、输入输出、错误语义、不变量、非目标、数据与权限、AI 行为版本、验收、成本/时延护栏，以及哪些差异允许由 target adapter 决定。未定义的差异不能被 adapter 私自补成产品决定。

### 6.2 Shared transforms

只有两个以上目标确实共享、且共享不会抹平目标语义时，才抽取 shared transform。每个共享点必须有调用方、契约、失败模式和跨目标验证。若共享层主要由条件分支、目标泄漏或不稳定抽象构成，消融后回到目标局部实现。

### 6.3 Conditional target adapters

只有同时满足下列条件才启用 adapter：

- 存在两个以上真实目标，或一个目标具有不可忽略的运行时/平台差异；
- canonical behavior 已足以判断相同与不同；
- 差异不能通过现有配置或简单参数安全表达；
- 有目标原生 validator，能在 adapter 出错时失败；
- adapter 的 owner、兼容面、回滚和退役条件明确。

否则保持单路径。不得为了未来可能支持的模型、端、数据库或 provider 预建 adapter。

### 6.4 Native validators

验证按风险相称顺序推进：

1. 最窄可失败的 fixture 或 unit/contract test；
2. canonical/reference behavior 检查；
3. 目标运行时、浏览器、provider 或端到端 native validator；
4. 受共享面影响时运行相关目标矩阵；
5. M09 以「claim → expected evidence → observed evidence → verdict → gap」独立审证。

任何层级失败都保留原始证据。不能通过弱化 canonical test、删除反例或让 judge 知道期望答案来制造通过。

### 6.5 Release and observation

A10 按实际目标逐项列 release readiness、配置/模型/Prompt/Skill/知识源版本、回滚和 R3 授权对象。A11/A12 按目标记录真实观测；共享指标只能用于比较，不能掩盖某一 adapter 的失败。新证据触发既有最小正确回退，而不是在 adapter 层永久打补丁。

## 7. 反面证据、停止条件与不可宣称内容

### 7.1 必须保留的反面证据

- capability spike 能完成任务，但用户仍不能理解、信任或高效操作；说明不能跳过 UX 验证。
- 单一模型在会议经验中表现好，但在同任务校准中范围违背或 review 负荷更高；说明固定路由失效。
- shared transform 减少重复，却引入大量目标分支或跨目标回归；说明抽象应消融。
- Skill candidate 相对 baseline 没有提升或只提高格式一致性；保留 null result，不晋升。
- reference test 通过而目标 native validator 失败；不得把目标失败归因于测试，先调查 adapter/runtime。
- RAG 提高召回但引入过期、越权、PII 或引用错误；先关闭相关路径并回到数据/检索契约。

### 7.2 停止条件

出现以下任一情况，停止当前实现并回退：canonical behavior 不可判定；规格、测试和用户最新意图冲突；目标权限或数据边界不清；没有能失败的 native validator；shared/adapter 范围持续扩张；同一问题三次验证不收敛；需要新增依赖、真实外部动作或生产权限但没有相应决定和授权。

### 7.3 当前不可宣称

本轮不能宣称：已经读取 Feishu 原始 transcript；三源方法具有因果关系；编译式交付优于现有流程；某模型天然适合固定岗位；fable-method 由 Anthropic 创建或认可；任何 Skill 已经通过真实 Agent、跨模型、生产或用户价值验证；静态文档、fixture 或检查通过即代表上线安全。

## 9. 验收标准

融合完成需同时满足：三源身份与限制可追溯；现有控制面仍是唯一状态与授权语义源；单目标任务不会被迫创建 adapter；多目标任务能从 A05 追到 shared/adapter/native evidence；模型路由有命名验证而非品牌断言；失败与 null result 不被删除；R3 外部动作仍需 Human `Own` 和当次对象级授权；真实行为未经评测时所有收益结论保持为待验证。
